2.1) загрузка на Github впервые (Файлы уже есть локально, на GitHub пусто)
git init						# 1. сделать из папки репозиторий, появляется скрытая папка .git, и Git начинает
							# отслеживать проект
git add .						# 2. подготовить изменения (собрать в "корзину" для коммита)
git commit -m "изменил то-то то-то"			# 3. зафиксировать версию ЛОКАЛЬНО (на GitHub ещё НЕ ушло!)
git remote add origin https://github.com/...		# 4. связать репозитории компа и GitHub(origin как адрес дома)
git branch -M main					# 5. назвать ветку main(как квартира в доме)
git push -u origin main					# 6. залить и закрепить связь между ветками на компьютере и GitHub

2.2) загрузить репозиторий в Github ПОВТОРНО
git add .						# подготовить изменения (собрать в "корзину" для коммита)
git commit -m "изменил то-то то-то"			# зафиксировать версию ЛОКАЛЬНО (на GitHub ещё НЕ ушло!)
git push                				# отправить зафиксированные коммиты на GitHub

Заметки:
origin — это просто короткое имя-псевдоним для длинного адреса GitHub
git remote add origin <url> = «запомни этот адрес под кличкой origin»

git branch -M main — что и когда?
  Переименовывает текущую ветку в main. Зачем: Git исторически создаёт первую ветку с именем master, а у GitHub стандарт
  — main. Чтобы имена совпадали, переименовываем. -M = переименовать принудительно. При клонировании это все делается

Что за -u в git push -u и чем отличается от git push без него?
  -u (= --set-upstream) при первой заливке запоминает связь между твоей локальной веткой и веткой на GitHub. Это
  делается один раз. Если бы ты не сделал -u, тебе пришлось бы каждый раз писать полную форму git push origin main

Только добавь привычку: на втором компе перед работой делай git pull (пункт 3.2) — чтобы забрать то, что залил с первого компа. Иначе версии разойдутся.
